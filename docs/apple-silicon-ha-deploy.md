# Apple Silicon HA deploy runbook

> Real runbook — based on the maintainer's working setup on a personal
> MacBook Air (M-series). Two-node failover, one-laptop reality.

## Goal

Run `phantom serve` (the phantom-mesh coordinator) in a configuration
that survives:

1. A single `phantom serve` process crash (auto-restart).
2. A laptop sleep / lid-close event (next wake re-joins the mesh).
3. A second M-series host being added without re-issuing tokens.

The maintainer's deployment uses **launchd + Docker Compose + Tailscale**
on Apple Silicon natively — no Rosetta, no x86 fallback.

## Layout

```
~/.phantom-mesh/
  agents.toml                # canonical config (generated by /onboarding/config)
  logs/
    phantom-serve.out.log
    phantom-serve.err.log
  data/
    cluster.db               # SQLite cluster state
```

## launchd unit (primary)

File: `~/Library/LaunchAgents/com.markl-a.phantom-mesh.serve.plist`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>            <string>com.markl-a.phantom-mesh.serve</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/local/bin/phantom</string>
        <string>serve</string>
        <string>--bind</string><string>0.0.0.0:7878</string>
    </array>
    <key>KeepAlive</key>        <true/>
    <key>RunAtLoad</key>        <true/>
    <key>ProcessType</key>      <string>Interactive</string>
    <key>StandardOutPath</key>  <string>/Users/USERNAME/.phantom-mesh/logs/phantom-serve.out.log</string>
    <key>StandardErrorPath</key><string>/Users/USERNAME/.phantom-mesh/logs/phantom-serve.err.log</string>
    <key>EnvironmentVariables</key>
    <dict>
        <key>PATH</key><string>/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin</string>
    </dict>
</dict>
</plist>
```

Load with:

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.markl-a.phantom-mesh.serve.plist
launchctl kickstart -k gui/$(id -u)/com.markl-a.phantom-mesh.serve
```

## Adding a second M-series node

1. On the new Mac, install Tailscale and `tailscale up` against the same
   tailnet.
2. On the primary, generate a join config:
   ```bash
   curl -s http://localhost:7878/onboarding/token | jq -r .token
   ```
3. On the new Mac:
   ```bash
   curl -s http://<primary-tailscale-ip>:7878/onboarding/config?token=<TOKEN> \
       > ~/.phantom-mesh/agents.toml
   phantom serve --bind 0.0.0.0:7878 &
   ```
4. On the primary, verify:
   ```bash
   curl -s http://localhost:7878/cluster/peers | jq .
   ```

## Failover behavior (current)

| Event | Behavior |
|---|---|
| `phantom serve` crash | launchd restarts within ~1 s (`KeepAlive`) |
| Laptop sleep | session pauses; resumes on wake via Tailscale reconnect |
| Primary offline > 30 s | secondary takes over coordinator role |
| Both nodes offline | mesh degraded; cached sessions survive in `cluster.db` |

## Known limits (be honest)

- **Single-laptop reality:** the maintainer has one Apple Silicon Mac,
  so the "second M-series node" path has only been exercised against an
  Intel Mac + an Asahi-Linux box. Full M-series-to-M-series HA is
  documented but not yet daily-dogfooded.
- No automatic data resync if `cluster.db` diverges — manual
  reconciliation required.
- macOS sleep is not "high availability" by any enterprise definition;
  this runbook is for **dev / SMB / single-engineer-shop** scale.

## When this graduates to "real HA"

- A second M-series Mac (Mac mini M-series for ~$700) is the unlock.
- Or, a customer brings two M-series Mac Studios — then this runbook
  becomes a paid pilot and gets stress-tested for real.
